CHAPTER 01

Database overview

AegisDB stores arbitrary byte strings in a durable, ordered key-value database. Applications can use Database directly or send JSON requests through the standalone HTTP server. Both paths use the same C++20 engine. PUT, GET, DELETE, atomic write batches, snapshot reads, bounded scans, explicit flush and compaction are implemented.

An LSM tree turns random logical updates into sequential WAL appends and immutable sorted files. That suits a write-oriented engine, while Bloom filters and sparse indexes reduce the work of point reads. C++20 provides explicit resource ownership, predictable binary layouts through codecs, efficient containers and owned worker threads. Networking uses Boost rather than a custom HTTP parser.

Validation boundary. Embedded persistence, fault/crash recovery and API routing have been exercised. The development sandbox prohibits localhost socket binds; real TCP integration is supplied but skipped here. Local process-crash tests are evidence for recovery behavior, not a physical power-loss test.

This release is single-node. There is no SQL, replication, consensus, authentication, compression or persistence of snapshots. It targets local POSIX filesystems on Linux and macOS; Windows and network filesystems are unsupported. The append-only manifest does not yet checkpoint its history.

CHAPTER 02

Complete architecture

Database is the public PImpl facade. DBImpl coordinates logical sequence state, mutable/immutable memtables, WAL association, installed tables and the maintenance lifecycle. Manifest maintains authoritative physical edits. Version is an immutable installed hierarchy whose shared table readers keep file handles alive.

One std::jthread serializes background flush and compaction. A separate maintenance mutex also serializes explicit compaction with that worker. This avoids conflicting compactions and lost version edits without a scheduler. The server has bounded socket admission, I/O threads, database request workers and one administrative job worker. Administrative jobs call the same embedded methods.

CHAPTER 03

Storage engine mathematical model

A record is (key, sequence, kind, value). Bytewise user keys sort ascending; versions of the same key sort descending by sequence. Kind is VALUE (1) or DELETION (2). An empty value is valid and differs from a tombstone. Empty keys and embedded zero bytes are valid.

(a.key, a.seq) < (b.key, b.seq) ⇔ a.key < b.key ∨ (a.key = b.key ∧ a.seq > b.seq)
visible(r,s) ⇔ r.seq ≤ s; winner(k,s) = arg max { r.seq : r.key = k ∧ r.seq ≤ s }

If the winner is a value, return its bytes; if it is a tombstone or absent, return NOT_FOUND. All structures use compareInternal or InternalLess. Batch sequences are consecutive, but the committed frontier jumps only after all nodes have been linked. No snapshot captures an intermediate sequence inside a batch.

inline int compareInternal(std::string_view a, Sequence as, std::string_view b,
                           Sequence bs) noexcept {
    const auto order = a.compare(b);
    if (order != 0)
        return order;
    return as > bs ? -1 : as < bs ? 1 : 0;
}

CHAPTER 04

Write-ahead log

FramedLog shares checked framing between WAL and manifest streams. A WAL file is named by a 20-digit file identity and .wal. Its 16-byte header contains the eight-byte magic AEGWAL01, little-endian version 1 and CRC32C of the preceding 12 bytes. Segments rotate with memtables when either configured target is crossed.

Frame offsetEncodingMeaning
0u32Payload length, at most 32 MiB
4u32CRC32C of payload
8u32CRC32C of length and payload-checksum fields
12bytesBatch payload: type u8=1, first sequence u64, count u32, records

Each batch occupies exactly one frame. There is no fragmentation and no partial replay. The header checksum protects the length, so a flipped length cannot masquerade as an incomplete tail. Decode validates kind, lengths, record count, sequence overflow and consecutive sequences before publishing the reconstructed batch. CRC32C uses the reflected Castagnoli polynomial 0x82f63b78, initial/final inversion and a deterministic lookup table.

void FramedLog::append(std::string_view payload, bool sync) {
    require(!payload.empty(), Code::invalid_argument, "empty log frame");
    require(payload.size() <= maxFrameBytes, Code::resource_exhausted,
            "log frame exceeds byte limit");
    Encoder e;
    e.u32(static_cast<std::uint32_t>(payload.size()));
    e.u32(crc32c(payload));
    e.u32(crc32c(e.bytes()));
    e.raw(payload);
    file_->append(e.bytes());
    if (sync)
        file_->sync();
}

Only an incomplete last frame of the newest required WAL is discarded. Complete checksum failures, including tail failures, are corruption. Older segments must be complete. Recovery truncates and synchronizes the accepted tail before creating a new segment. Rotation synchronizes the sealed segment even for ASYNC writes. Retirement follows a durable manifest edit that deletes the segment from the required-log set; an SSTable merely existing on disk is insufficient.

CHAPTER 05

Skip-list memtable

Each node owns its record and a vector of non-owning forward links. A vector of unique_ptr<Node> owns every node; growing the owner vector does not move node addresses. The sentinel is a fixed array of links. No node is individually removed while the memtable is alive.

P(H ≥ ℓ) = pℓ−1; default p = 0.25, maximum height = 16; expected seek/insert O(log n)
const SkipList::Node *SkipList::lowerBound(std::string_view key, Sequence sequence) const {
    const Node *cursor = nullptr;
    for (std::size_t level = maxHeight_; level-- > 0;) {
        auto *next = cursor ? cursor->next[level] : head_[level];
        while (next && compareInternal(next->data.key, next->data.sequence, key, sequence) < 0) {
            cursor = next;
            next = cursor->next[level];
        }
    }
    return cursor ? cursor->next[0] : head_[0];
}

prepare allocates every batch node and reserves owner capacity before WAL append. Capacity grows geometrically rather than reserving exactly one extra pointer per single-key write. publish links already-owned nodes without allocation. Memtable provides a shared mutex: writers take an exclusive lock for publication, GET takes a brief shared lock, and an ordered iterator holds a shared lock for its full lifetime. Immutable tables are frozen by removing the sole mutation path during rotation.

Memory accounting includes node/link/string capacities and unused owner slots, but is an estimate rather than allocator RSS. A bounded batch can overshoot the target. A scan’s mutable-table lock can delay publication; this is the deliberate initial concurrency tradeoff.

CHAPTER 07

Bloom filters

m = ceil(−n ln ε / (ln 2)²); h = round((m/n) ln 2); gi(k) = (H₁(k) + iH₂(k)) mod m

The SSTable builder emits one hash pair per distinct user key by comparing adjacent sorted keys, regardless of how many versions occur. Policy 1 uses two seeded FNV-1a passes followed by a specified 64-bit avalanche; H₂ is made odd. Unsigned addition/multiplication intentionally wraps modulo 2⁶⁴ before the bit-vector modulus. It never relies on std::hash persistence.

BloomFilter::Hash BloomFilter::hash(std::string_view key) noexcept {
    auto fnv = [key](std::uint64_t seed) {
        auto h = seed;
        for (char c : key) {
            h ^= static_cast<unsigned char>(c);
            h *= 1099511628211ULL;
        }
        h ^= h >> 33;
        h *= 0xff51afd7ed558ccdULL;
        h ^= h >> 33;
        h *= 0xc4ceb9fe1a85ec53ULL;
        return h ^ (h >> 33);
    };
    return {fnv(14695981039346656037ULL), fnv(7809847782465536322ULL) | 1ULL};
}
Excerpt from line 6. Current implementation.

The filter has at least 64 bits for a nonempty input and between 1 and 30 probes. The default target is 1%. Encoding persists format, hash policy, bit count, probe count and all bits. An empty filter has zero bits/probes and returns false safely. Decode enforces shape and allocation bounds; the enclosing SSTable checksum protects the serialized bytes.

A negative result skips an entire SSTable. A positive result still requires index selection and a block search. Tests check no false negatives at three configured rates and empirically bound observed positives without requiring an exact finite-sample rate. Bloom checks and negative decisions are counted separately.

Sparse block index

Every nonempty block has one entry: its final internal key, byte offset and encoded length. Separators are strictly ordered. For target (key,snapshot_sequence), lower_bound selects the first block whose final key is at or beyond the target. This is a coverage index derived from block boundaries, not a full per-record or popularity index.

std::size_t SSTableReader::selectBlock(std::string_view key, Sequence sequence) const {
    const auto it =
        std::lower_bound(index_.begin(), index_.end(), std::pair{key, sequence},
                         [](const IndexEntry &e, const auto &target) {
                             return compareInternal(e.separator.key, e.separator.sequence,
                                                    target.first, target.second) < 0;
                         });
    return static_cast<std::size_t>(it - index_.begin());
}

Point read path

The read view is captured as one state transition: a reader sees either the old immutable source plus old installed version, or the newly installed table. Rotation cannot create a gap. Subsequent writes may insert into a pinned mutable table, but their sequences exceed the captured frontier and remain invisible. Every candidate competes by sequence; source ordering alone never determines the winner.

CHAPTER 10

Range scans

Each memtable and overlapping L0 SSTable exposes a RecordIterator. Disjoint files in each deeper level become one TableSequenceIterator: a binary range seek selects the first table, and only the current table loads a block. This avoids pinning one data block for every deeper file. MergingIterator uses std::priority_queue ordered by internal key, with source identity breaking exact ties. Advancing a heap winner advances only that source.

capture read view at sequence s
seek all sources to max(start, after)
while heap has a record in [start,end):
    key = smallest user key
    consume all versions of key in descending sequence order
    winner = first record whose sequence <= s
    skip if winner is missing, deleted, or key <= after
    append winner if result and byte budgets permit
    return exclusive continuation at the last emitted key when bounded

The engine never materializes the complete database for a scan. Record-data memory is bounded by the admitted memtables, overlapping L0 sources, one current block per deeper level and the output page. Table references and resident indexes still grow with file count. Duplicate physical versions of a key produce one logical result. The merge consumes all versions of a key before returning its value, so versions spanning files or blocks cannot leak duplicate rows.

Scans return ascending bytewise keys over a half-open range. Pagination uses an explicit exclusive user key; it has no hidden snapshot change. Embedded callers reuse a Snapshot; server clients reuse a generation-qualified snapshot ID. An absent snapshot gives each page a fresh frontier. A continuation may be conservative when remaining rows are deleted.

Snapshots and MVCC

EventCurrent GET(x)Snapshot GET(x)
PUT x=A, sequence 10A—
Create S at frontier 10AA
PUT x=B, sequence 11BA
DELETE x, sequence 12NOT_FOUNDA

SnapshotState owns an ordered map from sequence to active token count. Creating a snapshot occurs under the database state lock and then the snapshot mutex, registering the committed frontier. Copies share a SnapshotToken; the token destructor decrements the map only when its final owner releases it. A handle can outlive the database because its registry has separate shared ownership.

cutoff = oldest active snapshot, or captured committed frontier if none; retain all seq > cutoff and the first seq ≤ cutoff for each selected key

Compaction uses this conservative cutoff. New snapshots created during compaction cannot require a sequence earlier than the captured frontier, while older existing snapshots were registered before input selection. Read operations pin their pre-compaction Version and memtables; file reclamation respects those pins. Snapshot tokens do not need to pin obsolete physical files after their historical winners have been preserved in replacement tables.

Handles belong to a particular database instance. Using one after reopen or with another database returns INVALID_ARGUMENT. Server handles have a bounded TTL, explicit deletion and periodic cleanup. Neither embedded nor server snapshots survive restart. Releasing snapshots permits further historical cleanup; explicit compaction can rewrite bottom-level files to reclaim retained versions and tombstones.

CHAPTER 12

Memtable rotation and flushing

Rotation is serialized with mutation admission. It synchronizes the old WAL, registers the successor segment through the manifest and swaps the active/immutable associations under the state lock. Capturing the replacement queue while holding the manifest-installation mutex prevents a concurrent completed flush from being reintroduced. An immutable source is never modified.

flushOne selects the oldest immutable source and streams its iterator into a builder outside the global state lock. It opens/verifies the finished output, prepares a replacement Version, then commits AddFile plus DeleteLog and the new WAL floor as one logical edit. Publication replaces the Version and removes the immutable in one critical section. Only then can the old WAL be removed.

The immutable queue is bounded. Admission waits on a condition variable and returns BUSY at the configured timeout. One bounded batch can overshoot the mutable target; it is frozen immediately when capacity permits, otherwise the next write waits. A failed flush retains the memtable and dependent WAL and puts the engine into fail-stop write mode. Recovery can reconstruct the source; automatic blind retries are deliberately absent.

Level organization

capacity(Lℓ) = levelOneBytes × Rℓ−1, for ℓ ≥ 1; default R = 10

Direct flush outputs enter L0 and may overlap. Levels 1 through the configured final level contain sorted, strictly disjoint inclusive user-key ranges: the previous file’s largest key is less than the next file’s smallest key. A user key is never split across adjacent compaction outputs, even if that group exceeds the output-size target.

LevelRead selectionCompaction pressure
L0All ranges containing the keyFile count / l0CompactionFiles
L1+Binary search by largest user keyStored bytes / configured capacity
Final levelSame disjoint range searchNo automatic next-level promotion; explicit rewrite can reclaim history

Every manifest file record carries identity, level, encoded file size, user-key bounds and sequence bounds. Manifest replay validates level ranges and duplicate identities. Increasing level count on reopen is supported; decreasing it below existing installed levels fails validation. File identities are reserved durably before use and never reused, including orphan identities found during recovery.

L0 admission is bounded even with automatic compaction disabled. Maintenance can temporarily add at most the bounded queued flushes beyond the stop threshold. In manual mode, explicit compaction first merges existing L0 to free room before flushing active data. Larger ratios reduce the number of levels but change overlap and write/read amplification; no universal optimum is claimed.

Leveled compaction

The automatic picker scores L0 by count and deeper source levels by size. L0 uses every current L0 input to simplify overlap closure. Deeper automatic compactions select the first source file from the highest-scored level and all its next-level overlaps. Explicit compaction uses all files in each source level for a deterministic sweep. If only bottom-level files remain, it rewrites that level in place for historical cleanup. The executor groups disjoint inputs from each deeper level into a lazy table sequence; L0 inputs remain separate heap sources.

Manifest and installed versions

CURRENT contains the exact name MANIFEST-000001 plus newline. The pointer is installed using a synchronized temporary file, atomic rename and directory sync. A missing pointer in an already edited manifest is corruption. A partial initialization header can be recreated only when no reserved WAL/SSTable identity exists: no acknowledged mutation was possible at that boundary. The manifest uses magic AEGMAN01 and the same checksummed frame envelope as the WAL.

Explicit AddLog/DeleteLog sets let recovery detect a missing segment between other file identities. The manifest is authoritative for live SSTables; directory scans are used only to reserve orphan identities and safely clean non-installed files. Manifest::commit prepares and validates a copied state, appends/synchronizes the edit, then replaces its durable-state mirror. applyVersion prepares the separately pinned runtime hierarchy.

void Manifest::commit(const VersionEdit &edit) {
    auto next = state_;
    apply(next, edit);
    const auto payload = encodeEdit(edit);
    log_->append(payload, true);
    state_ = std::move(next);
}

The committed frontier is the maximum of manifest state and all replayed complete batches. Required WALs are replayed even if their sequences are below the manifest frontier, because rotation may have recorded a frontier while those records still live only in WAL/memory. Recovery drains old segments before serving requests, keeping the runtime immutable queue within its configured bound.

Missing required files, truncated live SSTables, unsupported formats and complete checksum errors fail open. A numbered unregistered WAL at or above the retirement floor must contain only an initialization header. If it has record bytes, recovery rejects possible lost manifest history instead of silently deleting acknowledged data. Orphan cleanup touches only reserved numeric WAL/SSTable/temp names and CURRENT.tmp, preserving unrelated files. There is no salvage mode.

verifyTablesOnOpen defaults true and reads every data block; disabling it leaves data validation until a block is accessed. Checksummed metadata and file-size agreement remain mandatory. Crash tests use SIGKILL and injected abrupt process exits at persistence boundaries, not only graceful close.

Concurrency model

Lock / boundaryProtectsImportant rule
writeMutex_ (timed)Serialized mutations and rotationValidation precedes admission; bounded timeout
stateMutex_Read-view capture, committed frontier, publication, failure stateNever held across WAL sync or full table writes
Memtable shared_mutexSkip-list links and ownershipScan iterator holds shared access through its page
manifestMutex_File allocation and durable edit installationQueue capture and version install serialize here

Mutations validate, assign sequences and preallocate outside the state lock, append/sync WAL, then take state and memtable locks for atomic publication. Read views pin a consistent collection before any I/O. Rotation and flush publication use the same state boundary. Manifest commits hold the installation mutex across synchronization but do not hold the read-view lock.

The maintenance worker sleeps on a condition variable and owns its lifetime through std::jthread. It wakes for queued flushes or scored compaction. Backpressure similarly waits on a condition variable. There are no detached threads or polling loops in the engine. A storage error wakes blocked writers and disables further acknowledgments.

Database destruction requires callers to have finished all API calls. It stops/joins the worker and synchronizes the active WAL; destruction does not require flushing it into a table because recovery can replay it. The server closes admission, cancels sessions, joins storage/job workers and drains cancellation completions. A snapshot token can outlive its engine without using destroyed locks.

CHAPTER 19

Server architecture

Boost.Asio provides TCP, strands, signals, deadlines and owned thread pools. Boost.Beast parses HTTP; Boost.JSON parses JSON. Sessions use beast::tcp_stream deadlines and a bounded request parser. The listener creates each session on its own strand and limits live connections. Excess sockets are closed before request parsing, keeping request-worker admission bounded by the connection count.

Database calls run on the configured request pool, so WAL sync and GET/SCAN disk work do not run on I/O threads. Admin requests enqueue bounded jobs on one separate worker and return 202 with a status ID. Snapshot TTL cleanup runs on a steady timer. Router exceptions become category-only JSON errors, while operator logs carry infrastructure context.

Configuration controls host, port, database directory, worker/I/O counts, connection/request limits, timeouts, registry sizes and engine options. Defaults are localhost, port 8080, two I/O threads and four database workers. The initial protocol closes each connection after one response and has no optimized custom wire format, TLS or authentication. Socket deadlines do not cancel an admitted filesystem operation.

The real server executable is compiled. The supplied TCP suite exercises requests, concurrency, oversized bodies, restart and shutdown, but cannot execute in this sandbox because bind() is prohibited. Router tests exercise actual handlers and storage without making a claim about socket behavior.

Excerpt from line 16. Current implementation.

The write API validates the complete batch before modifying durable state. Preallocating skip-list nodes avoids acknowledging a persisted batch that cannot be linked due to a later ordinary allocation failure. The implementation intentionally synchronizes before publication; this is a stronger ordering than exposing data while durability synchronization is still pending. Snapshots and current reads see only the committed frontier.

SYNC acknowledges only after WAL sync and successful publication. ASYNC skips the device sync at this point. Rotation still seals/syncs segments and durably records successor association. A post-publication backpressure timeout postpones rotation while the already committed mutation succeeds; before-publication BUSY does not commit. A persistence error fails stop and can still leave an unacknowledged complete batch for recovery.

The guarantee assumes a local POSIX filesystem/device honoring file and directory fsync, same-directory atomic rename and advisory locking. Existing ancestor directory names must already be durable; newly created ancestors have their parent entries synchronized. macOS additionally requests F_FULLFSYNC where supported. No physical power-loss guarantee has been experimentally established in this session.

CHAPTER 21

Complete GET walkthrough

The HTTP router decodes the user key and resolves an optional snapshot handle. Unknown or expired handles produce 404 before reading storage. Database::get forwards to DBImpl, which captures the frontier and source lifetimes under the state lock. It does not duplicate storage logic in the router.

The mutable and immutable skip lists seek the internal target and return at most one visible candidate each. L0 readers first reject non-overlapping file ranges, then consult Bloom filters. Each deeper level binary-searches its disjoint file ranges. Positive Bloom results enter the sparse-index and in-block binary searches. All candidates compete by sequence, so a newer tombstone masks every older value regardless of where it resides.

std::optional<Record> SSTableReader::get(std::string_view key, Sequence sequence) const {
    if (key < meta_.smallest || key > meta_.largest || sequence < meta_.minSequence)
        return {};
    ++metrics_.bloomChecks;
    if (!bloom_.mayContain(key)) {
        ++metrics_.bloomNegatives;
        return {};
    }
    const auto index = selectBlock(key, sequence);
    if (index == index_.size())
        return {};
    const auto block = readBlock(index);
    const auto it = std::lower_bound(block->begin(), block->end(), std::pair{key, sequence},
                                     [](const Record &r, const auto &target) {
                                         return compareInternal(r.key, r.sequence, target.first,
                                                                target.second) < 0;
                                     });
    if (it != block->end() && it->key == key)
        return *it;
    return {};
}

CHAPTER 22

DELETE and tombstones

DELETE creates a DELETION record with a new sequence and empty payload. It follows the identical write-batch/WAL/publication path as PUT. No in-place SSTable removal occurs. A current read returns NOT_FOUND if that tombstone is the greatest visible sequence, while an older snapshot can still read an earlier VALUE.

L0: (k,20,DELETION), L2: (k,5,VALUE,old) ⇒ current GET(k) = NOT_FOUND

Removing the L0 tombstone without covering L2 would resurrect old. The executor therefore checks every unprocessed file range before dropping a retained base tombstone. If any range can contain that key, the tombstone survives. If complete coverage and the snapshot cutoff prove it redundant, dropping the tombstone also drops older selected values; the logical result remains absent.

Retention is conservative: file-range overlap may keep a tombstone even when no actual older value exists. New active memtable mutations have later sequences and cannot introduce an older installed value after the check. Background maintenance is serialized, so concurrent table installation cannot invalidate the selected coverage. Explicit bottom-level rewriting after snapshot release can safely produce no output, which the manifest installs as only input deletions.

CHAPTER 23

Performance and resource accounting

Insertion is expected O(log n) in the skip list plus sequential WAL bytes and optional synchronization. A point lookup consults bounded memtables, all L0 candidates and one candidate per deeper level; each table adds Bloom probes, O(log blocks) sparse search and O(log records/block) search. A scan/compaction over N internal records and K sources is O(N log K). K counts overlapping L0 inputs and one ordered source per deeper level, plus memtables for scans. Record/block memory streams; table metadata and open-file handles remain resident.

The LRU cache uses an unordered map and list under one mutex. Its key is monotonically unique file identity plus block offset. Only decoded immutable blocks are cached. Insertion charges vector/record/string capacities; map/list and allocator overhead are not charged. An evicted block pinned by a reader remains alive outside resident cache accounting. Frequently accessed metadata/indexes stay in table readers.
